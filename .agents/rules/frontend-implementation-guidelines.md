# フロントエンド実装ガイドライン：車輪の再発明を防ぐ

対象: `frontend/` 配下でのコード実装（人間・AIコーディングエージェント共通）

## 基本方針

**DOMイベントの手動購読（`document.addEventListener` による外側クリック検知、Escapeキー検知、フォーカストラップなど）を新規に書く前に、まず `package.json` の依存関係で同等の機能が既に提供されていないか確認すること。**

UIの「開閉」「フォーカス管理」「キーボード操作」はブラウザ間の差異やアクセシビリティ考慮が多く、自前実装は一見動いても以下のようなエッジケースを見落としやすい：

- タッチデバイスでの `mousedown` / `touchstart` の二重発火
- ネストしたポップオーバーの扱い
- フォーカスの戻し先（closeした後どこにフォーカスするか）
- スクリーンリーダー向けの ARIA 属性
- SSR環境での `document` 未定義ガード

これらは大抵、既に入っているライブラリ側で解決済みであることが多い。

## 具体例：`react-datepicker` のケース

このプロジェクトには `react-datepicker` (`^9.1.0`) が既に依存関係に入っている。

このライブラリは **非inlineモードのデフォルト挙動として**、以下を内部で処理している：

- 外側クリックでの自動クローズ（`react-onclickoutside` を内部で利用）
- Escapeキーでのクローズ、および閉じた後の入力欄へのフォーカス復帰
- `onClickOutside` prop でのカスタムハンドリングフック

→ **カレンダーの開閉に伴う「外側クリック / Escapeで閉じる」を独自の `useEffect` + `addEventListener` で実装する必要は、通常ない。**

もし独自カレンダーUI（`react-datepicker` を使わない完全自作コンポーネント）である場合は話が別だが、その場合もまず「なぜ `react-datepicker` の `customInput` / `renderCustomHeader` 等のカスタマイズ機能で足りないのか」を先に検討すること。

## 実装前チェックリスト

新しいインタラクション（開閉、ドラッグ、フォーカス制御、バリデーション等）を実装する前に、上から順に確認する：

1. **既存の依存ライブラリで完結しないか？**
   - フォーム・バリデーション → `react-hook-form` + `zod` + `@hookform/resolvers`（既に導入済み。素の `useState` によるバリデーションを新規に書かない）
   - 日付選択 → `react-datepicker`
   - ルーティング・遷移制御 → `react-router-dom`
2. **ブラウザ標準API・HTML要素で足りないか？**
   - モーダル・ダイアログ → `<dialog>` 要素の `showModal()`（Escape・フォーカストラップがネイティブで付属）
   - シンプルなポップオーバー → `popover` 属性
3. **それでも自作が必要な場合**
   - 一度きりの単純なロジックならその場で実装してよい
   - 同種のロジック（開閉・dismiss系）が複数箇所で必要になりそうなら、ライブラリ導入を検討する（下記）

## 新規ライブラリ導入の判断基準

上記1・2で解決できず、かつ「外側クリックで閉じる」「Escapeで閉じる」「フォーカストラップ」のようなUIプリミティブがプロジェクト内で今後も繰り返し必要になりそうな場合は、自作を重ねる代わりに以下のいずれかの導入を検討する：

- **`@floating-ui/react`**：ポップオーバー・ツールチップ・ドロップダウンの位置決め＋ `useDismiss` によるクリック外/Escape処理を提供
- **Radix UI (`@radix-ui/react-*`)**：`Popover` / `DropdownMenu` など、アクセシビリティ込みで挙動が完結したヘッドレスコンポーネント

ただし **「今まさに必要な1箇所のためだけに新規ライブラリを入れる」のは避ける**。2〜3箇所で同じパターンの自作コードが重複し始めたタイミングで導入を検討すれば十分。
